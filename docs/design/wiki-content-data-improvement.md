## 1. 要解决什么

当前库不是空的，而是**中间记忆很多、编译层和导航层对不上**。数据修复的目标是：

1. 阅读路径闭合：笔记能打开对应资料，没有指向不存在文件的 `[[sources/uuid]]`。
2. 有存量的项目有一篇权威项目页，能回答当前目标、生效决策、未决问题。
3. 过时结论不再和现行方案并列显示为 `active`。
4. 类型放错的页面挪走或降级，避免方法/成果被一次性事件占满。
5. 多轮已结束或实质停更的对话有会话页，归纳不再只看见叶子 turn。

不在本方案内：改分批算法、改证据写死字段、改 Completed 触发（属 Agent 方案）。数据回填可以**临时借用**现有 `wiki_synthesize` / `session_rollup` 任务，但验收看 vault 文件，不看「任务成功」。

## 3. 现状约束（修数据时不要踩）

- `raw/` 只读。修复不得改原始会话正文。
- 页面 `<!-- codeg-content -->` 内是代码维护区；人工补充写在校验标记之后。回填若走宿主提交，会重写维护区，必须先备份或先看 diff。

### 4.2 机械修复（不调用模型）

**来源链接。** 有 raw 文件的，把悬空 `[[sources/{id}]]` 改成 `[[raw/sessions/{id}]]` 或 `[[raw/imports/{id}]]`（与真实路径一致）。不要先造空的 sources 页再链上去充数。

**来源阅读页（若决定补）。** 合同要求 `sources/{source-id}.md` 是派生阅读页。最小可用页包含：标题（优先用已有 turn 标题，其次 `original_filename`，禁止用首句 prompt 截断）、来源种类、发生时间、指向 raw 的链接、已贡献笔记（从 `wiki_contribution` 或 turn 的 `codeg_source_id` 反查）。正文不要复制整份 raw。

**资料 index 标题。** `library.rs` 用 `wiki_source.source_title`。对仍为空或明显是用户第一句指令的标题，回填为对应 turn 标题或导入文件名。这是数据库字段 + 下次刷新，不是手改 `sources/index.md`（刷新会覆盖）。

**去掉重复「来源」节。** 对 records / decisions / outcomes / methods / concepts：若连续两节 `## 来源`，保留带可读标题的一节，删除只重复路径的那一节。

**YAML 项目字段。** 在对应 `work/projects/{slug}-{id}.md` 存在之前，不要把 UUID 改成断掉的 wikilink。顺序：先有项目页，再把编译页 `projects` 改成 `'[[work/projects/…]]'`。turn 页可继续保留 `codeg_project_binding_id`，另增 `projects` 列表。

验收：断链为 0；双「来源」为 0；打开任意一篇 9-16 日归纳页，来源可点到现存文件。

### 4.3 会话页回填

对象：同一 `codeg_conversation_id` 下 ≥2 篇 turn，且没有 session 页的对话。快照里至少包括 784、783、543、781、771、780、751、701、787 等。

做法：

1. 对话在库里已是 `Completed` 的，走现有 `session_rollup` 入队（去重键 `session_rollup:{id}`）。

Session 正文必须按主题收口「这次对话做成了什么、当前有效结论、未决」，禁止按回合拼接。原料是已有 turn，不够再读 raw。

`AGENTS.md` 目前三行占位。数据修复时应写成**用户偏好**（宿主禁止模型改这个文件）：

## 8. 2026-09-19 复盘：问题应拆成数据类和 Agent 运行类

前面的快照主要描述“库里已经有什么”。继续观察自动化任务后，需要把**数据结果**和**产生数据的运行过程**分开判断，否则会把“代理回合正常结束”误认为“Wiki 已经整理正确”。本节依据 `/Users/jiangyayun/.codeg/logs/codeg.2026-09-18.log`、`codeg.2026-09-19.log` 和 vault 的 `wiki-task.md`、批次 `verification.json` 做复盘；日志时间为 UTC，数量以各批次自己的快照为准。

### 8.1 数据类问题：已经落盘的内容仍有质量和可追溯性缺口

#### D1. 页面数量增长快，但知识层仍明显偏向 turn

第十六批验收记录为 344 个文件、341 个 Markdown、237 个可整理页面；随后后台又产生自动 turn 和索引增量。当前读取快照约为 347 个文件、344 个 Markdown、240 个可整理页面，其中 `work/turns/` 仍有 155 篇 `turn-summary`，实际的项目页、会话页和职责页仍只有少量人工补齐页，`capabilities/` 和 `sources/` 仍只有索引壳。

这说明“新增页面数”不能作为整理完成度。当前主存量仍是事件序列，项目、会话、职责、实体、能力和来源之间的汇总关系需要单独验收。批次验收应同时报告：新增页、更新旧页、被合并的页、仍未形成权威页的 binding，以及新增的过程记录数量。

#### D2. 整理过程被写成普通业务记忆，来源身份不够明确

第十二、十三、十四批已经发现：整理任务自身会产生 `work/turns` 摘要，`metadata/folders/` 也会登记 `automation/1/run-12`、`run-13` 等工作树。它们可以帮助追溯任务，但不是新的业务事实、项目进展或个人能力证据。当前这些页面仍以普通 `turn-summary` 或 metadata 页面存在，必须靠后续人工审计才能排除“过程回流”。

应在页面或来源元数据中区分至少三种来源：业务原始会话、Wiki 整理过程、外部项目元数据。整理过程默认只能进入审计/进度入口，不得参与项目、实体、方法或能力的事实汇总；除非明确声明它引用了哪份业务来源。

#### D3. 截断和脱敏状态没有成为数据入口门禁

当前 `raw/sessions/` 至少有 15 份 `codeg_truncated: true`，其中 6 份带 `codeg_redacted: true`。第十五、十六批已经遵守 `source_reported` 边界，但这是人工整理时补上的纪律；页面结构本身仍允许从截断来源生成看似完整的工作记录。

截断来源可以作为“待补证索引”，不能直接贡献当前结论、测试通过、生产验收或能力证据。页面必须展示来源完整性，且来源不完整时禁止自动升级 `verification_status`；若没有对应 turn-summary，也只能生成缺口记录，不得按标题或工具观察补造正文。

#### D4. 自动索引与人工入口存在双重所有权

`work/projects/index.md`、`work/sessions/index.md`、`work/areas/index.md` 和 `work/records/index.md` 同时包含自动生成区域与人工导航。当前会话索引仍保留“自动归档的对话汇总尚未形成”的说明，但目录中已经有人工建立的三篇会话页；这会让人和 Agent 无法判断哪一段是当前入口。

这不是单纯的链接问题，而是页面所有权没有固化。每个索引需要明确“机器维护区”和“人工维护区”，机器刷新不得把人工入口当成冲突后静默跳过；若刷新失败，任务结果必须带出受影响路径，不能只在应用日志里留一条 warning。

#### D5. 全局快照会被后台增量改变，批次结果难以复算

第十六批验收已记录：整理期间 `metadata/` 被后台索引刷新，新增一个 folder 文件并刷新了 44 个既有文件；第十四批也遇到同类的后台增量。批次声称“未修改 metadata”在字节层面可以成立，但全局数量和页面集合已经发生变化。

因此，批次基线必须同时保存文件清单、内容哈希、后台增量清单和任务时间窗。验收要区分“本任务修改”“后台并发修改”和“预先存在的脏数据”，否则后续复核无法判断数量变化来自整理质量还是索引刷新。

#### D6. `log.md` 不能反映 Wiki 变更历史

当前 `log.md` 正文只有 11 条 `import succeeded` 记录；在连续自动化任务和多批整理已经产生大量 turn、项目和工作记录的情况下，看不到 turn-summary、session-rollup、synthesize、冲突、跳过或失败恢复的幂等收据。提交 JSON 和应用日志各自保存了一部分信息，但没有一个面向 Wiki 的统一变更账本。

至少应能从一条任务收据回答：输入来源、任务类型、模型回合、提案/页面操作、实际写入、跳过原因、warning、重试次数和最终状态。没有这条链，出现重复页、空成功或旧结论未更新时只能靠人工猜测。

### 8.2 Agent 运行类问题：任务链路没有把“完成”定义到内容结果

#### R1. ACP `end_turn` 只证明模型回合结束，不证明 Wiki 任务成功

自动化日志在连续窗口中观察到 `run-1` 至 `run-16` 的 ACP 连接；每个 run 都出现 `turn_complete ... stop_reason=end_turn`，部分 run 还出现子 Agent 工具标题改写。这个信号只能说明代理回合结束，不能证明项目权威页已更新、来源完整、页面类型正确或人工区域未被覆盖。

运行状态需要至少拆成：`agent_finished`、`proposal_validated`、`vault_write_applied`、`navigation_refresh`、`content_checks_passed`。只有最后一个状态满足本批验收，才能把任务标记为成功；没有页面写入也必须明确记录为“无内容成功”或“需要重试”，不能和已完成整理混用。

#### R2. 任务关联存在竞态，连接生命周期与内容幂等没有合并

第十五、十六个自动化 run 的日志出现 `send_prompt_linked: conversation resolved but external_id not yet on state`。第十六个 run 完成后，同一工作树和会话又出现重新初始化、`dedup_wait ... outcome=ready` 和再次断开。日志没有证明发生了重复写入，但已经说明“会话关联、重连、去重和页面提交”是分开的状态机。

任务应使用稳定的 `automation_run_id` 和 `input_fingerprint` 做幂等键，提示发送、模型回合、提案提交和页面写入都沿用同一键。重连只能恢复未完成阶段；已写入页面的阶段必须返回原收据，不能因为 ACP 会话重新建立而重新消费输入。

#### R3. 多 Agent 配置和实际能力不一致

每次 Codex 自动化连接都记录了“multi-agent delegation is enabled”，同时又记录由于 `CODEG_ACP_HOST_TOOLS=agent`，委派能力被 withheld。日志中虽可见若干 `subagent detected`，但不能据此证明任务获得了独立的文件系统、终端或模型委派能力。

任务提示和验收不能把“设置已开启”当成“委派已可用”。运行合同应显式暴露本次可用能力；若委派被抑制，任务应降级为单 Agent 流程并在收据中说明，不应生成带有并行核验语义的结果。

#### R4. 输入证据状态没有在运行前阻断不可靠整理

目前人工批次可以识别截断、脱敏和缺少 turn-summary 的来源，但自动化任务仍可能把这些来源放进普通整理上下文。提示词中的“注意证据边界”不足以替代宿主门禁，因为模型可能先生成一篇结构完整的页面，随后才在末尾加一句“待核验”。

宿主在组批前应计算来源完整性，并把 `truncated`、`redacted`、`missing_turn` 作为结构化输入状态；涉及这些状态时只能允许 `gap/audit` 类输出，禁止创建 `active` 的项目、成果或能力结论。该门禁与页面内容校验分开实现，不能只依赖 prompt。

#### R5. 导航刷新冲突被记录为 warning，但没有进入任务结果

2026-09-18 至 2026-09-19 的应用日志中，16 个 Wiki navigation refresh job 共出现 34 条 conflict warning，目标集中在 `work/records/index.md`、`work/areas/index.md` 和 `work/sessions/index.md`。这些 warning 没有阻止 turn-summary 提交，因此任务表面上仍可成功结束，但入口页可能停留在旧版本。

刷新冲突应有明确策略：机器维护区可自动重算；人工维护区只做受保护的增量合并；无法合并时任务状态至少为 `succeeded_with_warnings`，并把路径写入结果页和 `log.md`。不能仅依赖应用日志让使用者事后发现入口没有更新。

#### R6. 批次编排仍以“产出一篇摘要”为中心，未把旧页更新作为硬合同

十六批整理记录显示，很多工作仍由人工在自动摘要之后读取 turn、旧页、项目 metadata 和来源，再决定是否合并。自动任务产生的主要落点仍是新的 `work/turns`，项目页、实体页、职责页和能力证据需要额外批次补齐。这与已有 Agent 方案中“有 binding 必须 update/create 项目权威页”的要求不一致。

运行合同应在消费输入前先计算候选权威页；有项目 binding 却没有项目页提案时，本批不得把输入标记为 consumed。默认操作应是更新既有页，只有无法并入现有主题时才允许 create，并把近重复拒绝、supersede 和未决项写入验收结果。

#### R7. 运行验证只覆盖代理动作，未覆盖失败恢复和内容不变量

现有批次大量记录“未运行 Wiki 流水线、模型、业务测试或现场验证”，而自动化 ACP 日志只显示连接与回合生命周期。对长材料截断、来源缺失、读取告警、任务取消、重试、部分写入、重复提交和人工区域保护，仍没有一条可重复的端到端运行证据链。

这类测试应成为 Agent 运行类验收，而不是要求每次内容整理都重新做业务验证。至少要有一组真实长材料夹具和一组故障夹具，分别验证：输入不完整时不升级结论、读取失败时不消费、提交中断时可恢复、重复 run 不重复写页、索引冲突可见、原始树不变。

### 8.3 两类问题的处理边界

| 类别 | 先修什么 | 验收看什么 | 对应方案 |
| --- | --- | --- | --- |
| 数据类 | 来源完整性、过程记录标识、索引所有权、批次快照、变更收据 | 打开 vault 即可判断来源、状态、当前结论和未决；历史过程不会被当成业务事实 | 本文第 4～6 节及本节 D1～D6 |
| Agent 运行类 | 成功状态机、幂等键、证据门禁、项目分批、冲突回报、失败恢复 | 同一输入重复执行不重复消费；任务结果能解释写入/跳过/告警；有 binding 必须更新权威页 | [整理 Agent 提升方案](./wiki-organize-agent-improvement.md) 及本节 R1～R7 |

两类问题不能互相替代。把旧页面人工修好，不能证明下一轮任务不会再次生成同名页；把 Agent 流程跑通，也不能把已有截断来源、旧状态和错误分类自动变成可信知识。

### 8.4 调整后的优先顺序

```text
先做来源完整性和过程记录隔离
  → 再补任务收据、成功状态机和幂等键
  → 再固定索引的机器/人工所有权并处理冲突回报
  → 再按项目分批，强制 update 权威页后才消费
  → 最后继续做项目、会话、实体和能力页的人工回填
```

其中第一、二步是停止继续污染数据的门槛；第三、四步完成后，才适合扩大自动整理范围。当前不应以“自动化 run 数量”“turn-summary 数量”或“模型回合 `end_turn` 数量”作为 Wiki 整理完成度。

### 8.5 新增验收项

在现有第 6 节验收之外，增加以下检查：

1. 任一自动化任务都能从 `automation_run_id` 找到输入、模型回合、页面操作、warning 和最终状态；`log.md` 不再只有 import 记录。
2. 截断、脱敏或缺少 turn-summary 的来源只能产生缺口/审计记录，不能生成 `active` 的项目、成果或能力结论。
3. 整理过程摘要和工作树 metadata 被标注为过程来源，不进入业务项目、实体、方法或能力汇总。
4. 索引刷新冲突在任务结果中可见；人工入口不会因刷新被静默跳过，机器维护区刷新仍保持幂等。
5. 同一 `automation_run_id + input_fingerprint` 重试不会新增重复 turn、重复 record 或重复来源贡献；中断后可从未完成阶段恢复。
6. 有项目 binding 的批次若没有项目页 `create/update` 提案，不得标记输入为 `consumed`。
