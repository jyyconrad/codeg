# 06 — 部门内部业务：四类产品能力（FDE 切面）

| 字段 | 内容 |
|------|------|
| **结论先行** | FDE 作业对象是**双轨**：外线客户 engagement ∥ **内线部门业务**（四类产品能力落地 / 内部业务方 / 狗粮联调 / 回灌进对应产品）。**同一**所有权弧与 G1–G7；赞助人换成部门产品 Owner / 业务方。忌「内线只做人天、外线才叫 FDE」 |
| **对应总册** | [`../proposal.md`](../proposal.md) **§2 / §3** 作业对象扩展；可交叉 **§5 / §6**（工作台与 Agent 执行器仍挂 CodeG Option A，**不换栈**） |
| **硬约束** | **不推倒** CodeG Option A；不重写 Ontology / 工具 / 日课长文。**四类品类**为硬框架；部门示例产品名仅括号标注。门户 mock 功能描述仅 **软/示意** |
| **不写** | 捏造功能清单、ROI、价格、客户名、未给出的架构；智能客服 / 语音类**不编**功能列表 |

---

## 一句话（硬）

> 内线 = 用同一 FDE 模型，把部门**四类产品能力**接到真实内部业务工作流上：生产采用 + 写回闭环 + **回灌进对应品类/产品 backlog** —— 不是「帮忙调参」的人天池。

**四类（硬）：** 智能客服 · 知识库 · 语音 · AI Coding 工具。

---

## 1. 双轨作业对象（硬）

| 轨 | 服务对象 | 赞助人 / 签字方 | 成功仍看 | 回灌去向 |
|----|----------|-----------------|----------|----------|
| **外线** | B 端客户 engagement | 客户 Sponsor + 业务 Owner + IT | G1∧G2∧G4（+G7） | 平台 / 行业模板 / 产品能力 |
| **内线** | 部门内部业务方 × **四类产品能力** | **部门产品 Owner** + 内部业务方 | **同一** G1–G7 | **对应品类/产品** backlog / playbook |

| 不变（硬） | 置换项（内线） |
|------------|----------------|
| 所有权弧：discovery → scope → build → production → adoption/handoff → productize | 「客户」→ 内部业务方；「现场」→ 部门业务环境 / 狗粮联调环境 |
| 度量三角 + write-back + G1–G7 | KPI 与业务方约定；写回目标 = 工单 / 知识条目 / 会话处置 / 代码仓等**类别** |
| 红线：Demo≠Prod、无回灌不做长期驻场 | 赞助人缺产品 Owner 签字 = engagement 不可闭环 |

链回：[`01-what-is-fde.md`](01-what-is-fde.md)（所有权弧）、[`03-value-get-work-done.md`](03-value-get-work-done.md)（G1–G7）。

---

## 2. 为何要写内线（硬）

| 理由 | 说明 |
|------|------|
| **最近回灌路径** | 内线成功模式 → playbook → 进**对应品类产品**队列 → 外线复制；比纯外部定制更短闭环 |
| **狗粮 / 联调** | 品类能力先在部门业务上跑通采用与写回，再对外讲「替人把活干完」 |
| **口径一致** | 内线成功仍按 adoption + workflow impact + eval；**禁止**把内线降级为「只做人天」 |

**反模式（硬）：** 「外线才叫 FDE，内线只是支撑/调参」→ 飞轮断裂，产品无学习。

---

## 3. 四类产品能力 × FDE 切面（硬框架 / 软细节）

> **列主轴 = 品类（硬）。** 「部门示例产品」仅括号示意，非正式对外品牌叙事。典型活写到**工作流级**；不编功能清单。门户 mock（如「星火知识库」「星火飞码」）描述标 **软/示意**，勿进合同。

| 品类（硬） | 部门示例产品（次要） | 典型「替人干完」的活（工作流级） | write-back 目标（类别） | 回灌去向 | 与 CodeG / Ontology 一句 |
|------------|----------------------|----------------------------------|-------------------------|----------|--------------------------|
| **智能客服** | 阡陌 | 客服会话处置闭环：从进线/意图到工单或知识缺口闭环，业务方可验收采用 | 工单类系统；会话处置记录；质检结论（类别） | **智能客服**类产品 backlog；知识缺口 → **知识库** | Ontology Lite 约束「可允许的会话动作」；调度仍可走 CodeG |
| **知识库** | （门户样例名「星火知识库」·**软**） | 业务知识上架采用；检索命中结果被下游工作流实际调用（非仅演示问答） | 知识条目 / 版本与权限状态；被工作流引用的命中记录（类别） | **知识库** backlog；常被智能客服 / 语音 / AI Coding **共用** | 语义与权限口径挂 Ontology Lite；勿把 mock「多源/图谱」当已交付规格 |
| **语音** | （用户点名品类；无具名部门示例则留空） | 语音通道上的业务动作闭环（外呼 / 坐席辅助等写到**品类层**，不编具体功能表） | CRM / 工单类系统写回（类别）；与智能客服可组合 | **语音**类产品 backlog；组合模式可回灌智能客服侧 playbook | 通道能力 ≠ 换栈；动作白名单仍属 Ontology / 控制面 |
| **AI Coding 工具** | 飞码（门户样例名「星火飞码」·**软**） | 研发工作流生产采用：补全 / 生成 / 评审辅助等到真实代码仓节奏（工作流级） | 代码仓 / PR / 评审结论等类别写回或留痕 | **AI Coding** 类产品 backlog | **与 CodeG Option A 互补、不换栈**：CodeG = 调度底座（项目/HITL/证据）；本类 = 部门 AI-Coding **产品能力** |

### 3.1 组合关系（硬纪律 / 软示意）

| 组合 | 说明 | 标注 |
|------|------|------|
| 智能客服 ↔ 知识库 | 质检 / 会话中的知识缺口 → 上架或修订知识条目 | 作业切面**硬**；具体接口**勿编** |
| 语音 ↔ 智能客服 | 语音通道进线 → 客服类处置闭环 | 品类组合**硬**；产品功能表**勿编** |
| AI Coding 工具 ∥ CodeG | 本类提供 AI-Coding 产品能力；CodeG 继续做调度 / HITL / 证据 / 项目编队 | **硬：不换栈、不推倒 Option A** |
| 知识库为其余三类共用底座（语义检索等） | 内线常先打通「知识被工作流使用」 | 共用关系**硬**；「多源接入/图谱」等来自门户 mock → **软/示意** |

## 4. 内线 engagement 最小工件（与 §3.2 同构）

| 阶段 | 内线必交付（压缩） | 签字 / 队列 |
|------|-------------------|-------------|
| Discovery | 内部业务问题一页纸 + 成功数字草案 + **涉及品类** | 业务方认可「值钱且可测」 |
| Scope / SOW | MVP 边界、非目标、写回目标类别、退出条件 | **产品 Owner 签字** |
| Demo / PoV | 可点击验证 + **「非生产」** + 环境剖面 | 不得直接当 Prod |
| Integrate / Harden | 连接器/权限/写回路径 + eval 门 | 与外线同纪律 |
| Adopt / Handoff | 内部采用证据；无原厂盯屏可运行 | 业务方 + 产品侧接手 |
| Productize | **≥1 回灌条目**进**对应品类/产品** backlog（非只进个人笔记） | 产品队列可见；对齐 G7 |

详表仍以 proposal **§3.2** 为准；本表只强调内线置换项。

## 5. 红线补充（硬 · 内线适用）

| # | 禁止 | 对齐 |
|---|------|------|
| I1 | 内线 **Demo = Prod** | 同 R2 |
| I2 | 内线长期「驻场/支撑」但 **零回灌**进产品队列 | 同 R1 |
| I3 | 把「**帮忙调参** / 答疑 / 人天忙」当 FDE 交货 | 同 R12 / R0——须 G1∧G2∧G4 |
| I4 | 无产品 Owner 签字的「内线项目」长期空转 | 同赞助人缺位 |
| I5 | 用门户 mock 功能列表写进合同 / DoD | 见下节软写 |
